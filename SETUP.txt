INSTALLING ON A NEW EMPTY HOST
1. Back up any existing website and database before replacing files.
2. Put the folders in the locations above, keeping private files outside the
   public website folder. Do not upload this entire source package publicly.
3. Create a separate MySQL/MariaDB database and a database user with access.
4. Import database/schema.sql into that EMPTY database. Never re-import the
   initial schema over an existing production installation.
5. Copy private/config.example.php to private/config.php outside public_html.
   Set environment='production', site_url='https://somanambiti.com', the actual
   database connection details, a random 64-character hexadecimal app_key,
   mail_from='info@somanambiti.com' and mail_transport='mail'. Generate secrets
   privately; do not put them in public files or commit them to source control.
6. Restrict config.php to the hosting account (normally permissions 0600).
7. Ensure a trusted certificate, the intended DNS records, HTTP-to-HTTPS and
   www-to-apex redirects, and an active domain mailbox are configured.
8. Check the actual mailbox delivery, verify a test account, save progress,
   sign out/in and check another device before considering the installation
   verified. Confirm external email-provider delivery as well as local mail.
The live site is already installed. These steps are for a new empty host.

recent 500 account trades remain in history. Journal limits are 200 entries
and 2,000 characters per field. Journal JSON export is a download, not a restore
format or a substitute for server backups.

SIGN-IN USABILITY AND SECURITY — 13 November 2026
Deploy public/auth-ui.js, auth-ui.css, the updated main app/index, speaking accounts/index, public/api.php, private/bootstrap.php and private/signin-security.php together. No schema change: security counters use the existing rate_limits table with distinct opaque HMAC keys. Keep every actual private configuration unchanged. The production patch contains no credentials.
Both sign-in surfaces, registration and password reset have independent Show/Hide controls, Caps Lock hints and password-manager autocomplete. Visibility resets on submission, dialog close, window blur and when hidden. Password paste remains allowed. Login pauses are displayed using the server's Retry-After value; changing the email only clears an email-specific UI pause. The server enforces every pause even in another tab/device or a modified client.
Five failed password attempts for a normalized email within 15 minutes pause further login attempts for 15 minutes from the fifth failure, across source addresses. Thirty failed attempts per actual REMOTE_ADDR in the observation window pause that connection. Blocked retries do not prolong the lock. The ordinary request limit is 60 sign-in requests per connection per 15 minutes. Successful sign-in clears only that email's failure counter, not the connection's failures. Unknown addresses behave the same as known accounts on failure. X-Forwarded-For supplied by visitors is never trusted. A valid single-use password-reset link clears the email pause and invalidates existing sessions; connection restrictions remain. Recovery requests retain their separate limits. Existing authenticated study sessions are not revoked by a failed login attack.
New or reset passwords require at least 15 Unicode characters and at most 72 UTF-8 bytes (the bcrypt limit); overlong values are rejected rather than truncated. Existing passwords continue to work. Sessions retain the existing two-hour idle timeout and now have an eight-hour absolute lifetime. Legacy sessions acquire a deadline when first seen after the update. Existing session rotation and HttpOnly/Secure/SameSite cookie protections remain.
PHP error logs receive signin_failed and signin_temporarily_blocked events with short keyed identifiers and a retry interval. No raw email, IP, password, cookie or token is logged by the new guard. These controls slow guessing and credential spraying; this release does not implement MFA, passkeys, an external CAPTCHA, breach-list screening or a hosting firewall.
Tests: tests/signin_security_api.py and tests/signin_security_unit.py use ONLY the dedicated localhost:8792 copy with .local/signin-security-config.php and signin-security.sqlite, not production. A correct password on an unrecognised browser creates only a pending sign-in, with no authenticated user_id. It sends a cryptographically random six-digit code and binds its HMAC to that server session, challenge and account security version. The code expires in ten minutes; the original password proof expires after fifteen minutes. Correct code completion also confirms an unverified email. Codes are single use. Resends require a 60-second account-wide wait and do not replenish guesses; at most five sign-in emails per account per hour, plus a connection limit. Password and code failures share the existing five-failure / fifteen-minute guard, so submitting a correct password again cannot reset code-guess limits. Delivery failure never grants access and leaves a retry path.
Remember this browser for 30 days is optional and OFF by default. The host-only hisa_device cookie is HttpOnly, SameSite=Lax and Secure on the live HTTPS site. Its random value is not stored in the database; the keyed hash binds it to the account security version. Trust has a fixed expiry and does not renew when used. A new browser/profile, cleared cookies or an expired marker asks for a code again. This recognises browser storage, not physical hardware or IP addresses. Students should leave it off on shared computers. My account and Speaking Studio offer Forget remembered browsers to revoke all markers for that account. Password recovery revokes every remembered marker and all older authenticated/pending sessions through session_version.
Private code values and browser tokens must not appear in logs, reports or packages. Development mail logging is allowed only for the existing development environment. Live email uses the configured PHP mail transport, already verified for recovery. Protecting the mailbox remains important; email two-step is not a phishing-resistant passkey or authenticator factor.
